# BurgerGo — User Accounts & Trip Sharing (Design)

**Date:** 2026-06-12
**Status:** Approved direction; spec for implementation planning.

## Goal

Add real user accounts to BurgerGo (web + expo-rn native app):

- Sign in with Google only. First sign-in registers the account; later sign-ins log in. No passwords.
- Session lasts 3 months (rolling — active use keeps you signed in indefinitely; 3 months idle requires re-login).
- Users can edit their display name and upload an avatar.
- Trips become multi-user: a trip has one **owner** and any number of **members**; users see only trips they belong to.
- From the trip edit UI, any member can invite others by email and see who currently has access.

## Decisions (settled with Eric)

| Question | Decision |
|---|---|
| Auth library | **Better Auth** (self-hosted; official Drizzle/SQLite adapter + Expo plugin) |
| Existing trips | Seeded to Eric's personal Gmail via `BURGERGO_OWNER_EMAIL` server env var — the address is **never committed** (public repo) |
| Permission model | All members edit equally; only the owner deletes the trip or removes members; members may leave |
| Inviting unregistered emails | Allowed — pending membership keyed by email, auto-claimed on first Google login |
| Enforcement scope | Everything requires login. Exception: photo/media GET routes stay tokenless (unguessable random ids; avoids auth headers on every `<img>`/`<Image>`) |
| Enforcement layer | Route-layer guards (`requireUser`, `requireTripMember`), not repo-layer rewrites |
| Machine access | Existing `BURGERGO_API_KEY` (`x-api-key`) remains as a server-to-server bypass that acts as the owner user (scripts, MCP tools) |

## Architecture

### 1. Identity layer (Better Auth)

- `src/lib/auth.ts`: `betterAuth({...})` with
  - `database: drizzleAdapter(db, { provider: "sqlite" })`
  - `socialProviders.google` (client id/secret from env; **one Web-type OAuth client** — the native app reuses the server-side web flow, no iOS client needed)
  - `session: { expiresIn: 90 * 24 * 60 * 60, updateAge: 24 * 60 * 60 }` (rolling 90-day session)
  - plugins: `expo()`, `bearer()`
  - `trustedOrigins`: app scheme `burgergo://` + dev origins
  - `baseURL` honors the `/burgergo` sub-path (`https://eric.month2month.com/burgergo`)
- Route handler at `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler`).
- New tables `user`, `session`, `account`, `verification` generated by the Better Auth CLI into the Drizzle schema; normal drizzle-kit migration (auto-applies via docker-entrypoint).
- Login hook (database hook on user create / session create): claim pending `trip_members` rows whose `invited_email` matches the new user's email (case-insensitive).

### 2. Trip membership

New table `trip_members`:

| column | notes |
|---|---|
| `id` | pk |
| `trip_id` | fk → trips, cascade delete |
| `user_id` | nullable — null while invite is pending |
| `invited_email` | lowercased; unique with `trip_id` |
| `role` | `'owner' \| 'member'` |
| `created_at` | seconds (project convention) |

- Creating a trip inserts an owner row for the creator.
- **Startup seed (idempotent, not a SQL migration):** for every trip with no owner row, insert `role='owner', invited_email = BURGERGO_OWNER_EMAIL`. Runs in the entrypoint after migrations; reads env, so it cannot be a static migration file.
- Invites: insert `(trip_id, invited_email, role='member')`. If a user with that email exists, set `user_id` immediately; otherwise it's pending until first login.
- Rules: members are equal editors; owner-only actions are delete-trip, remove-member; a non-owner member can remove their own row (leave). The owner cannot leave (must delete the trip instead) — keeps every trip owned.

### 3. API enforcement

- `requireUser(headers)` → Better Auth `getSession`; falls back to `x-api-key === BURGERGO_API_KEY` resolving to the owner user; otherwise 401.
- `requireTripMember(userId, tripId)` → 404 (not 403, to avoid existence leaks).
- Every `/api/*` route and every Server Action gets one or both guards. Child-resource routes that only carry a child id (photo list item, expense, ticket…) resolve the child → trip id first, then guard.
- `GET /api/trips` returns only trips joined through `trip_members` (claimed rows).
- Tokenless exceptions: `/api/auth/*`, photo/media GET routes (`/api/photos/*`, `/api/links/thumb/*`, poi-photo proxy).
- CORS stays `*` on `/api/*` (native app authenticates via bearer/cookie header, not ambient cookies, so `*` remains safe and keeps expo-web debugging working).
- New endpoints: `GET/POST/DELETE /api/trips/[id]/members`, `GET /api/me`, `PATCH /api/me` (name), `POST /api/me/avatar` (multipart).

### 4. Profile

- Display name + avatar editable. Name via Better Auth `updateUser`.
- Avatar: uploaded image → sharp → webp ≤512px stored under `uploads/avatars/<userId>.webp` (delete-guard under uploads root, same as photos); `user.image` stores the API URL; served by a small tokenless GET route like other media.

### 5. Web UI (Atlas Light recipes)

- `/login` page: cream logo field + "Continue with Google" button; unauthenticated visitors are redirected there (middleware cookie check is the coarse gate; routes/actions are the real gate).
- Settings → new **Profile** card: avatar (tap to replace), display name input, signed-in email (read-only), Sign out.
- Trip edit sheet → new **Members** section: avatar+name rows (pending invites show the email with a "pending" tag), member count, invite-by-email input, remove buttons (owner only), Leave (non-owner).

### 6. Native app (expo-rn)

- `app.json`: add `"scheme": "burgergo"`; new deps `@better-auth/expo` client, `expo-secure-store`, `expo-web-browser` → **native change ⇒ requires a new EAS build, not OTA**.
- `lib/auth.ts` client: `createAuthClient` with the Expo plugin (SecureStore-backed session).
- Login gate screen before the tab navigator: "Continue with Google" → system browser → redirect back via the scheme.
- `lib/api/client.ts`: attach the Better Auth session cookie/bearer header to every `getJson`/`writeJson`/`postForm` call (the Expo plugin exposes the stored cookie).
- Settings: Profile card (name, avatar via expo-image-picker, sign out) above the existing cards.
- Trip edit sheet: Members section, same behavior as web.
- Offline: cached JSON remains readable when offline even if the session can't be revalidated (guards run server-side; the client cache layer is unchanged).

## Rollout

1. Backend + web UI: migrate, seed, deploy. Web is immediately usable (Eric signs in with the seeded Gmail and sees all existing trips).
2. expo-rn: login flow + new build via `eas build -p ios --profile preview`; reinstall on phones.
   ⚠️ Once the backend deploys, the **currently installed app stops working** (403/401 on every call) until the new build is installed — do both steps back-to-back.
3. One-time Eric task: create a Web OAuth client in GCP Console; authorized redirect URIs `https://eric.month2month.com/burgergo/api/auth/callback/google` and `http://localhost:3000/burgergo/api/auth/callback/google` (dev). Secrets go to the server `.env` and local `.env` only.

## Testing

- Vitest: guard helpers (401/404 paths, api-key bypass), membership repo (invite, claim-on-login, leave/remove rules, owner seed idempotency), trips list filtering.
- `tsc` gate (web) + `npm run typecheck` (expo-rn) + `expo export` both platforms.
- Manual: two-account end-to-end (invite pending email → second account logs in → sees trip; non-member sees 404).

## Out of scope (YAGNI)

- Email notifications for invites, role tiers beyond owner/member, account deletion/export, non-Google login methods, per-resource permissions, sharing for restaurants/places outside a trip.
